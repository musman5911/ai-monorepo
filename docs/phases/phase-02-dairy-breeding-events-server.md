# Phase 2: Dairy breeding events: server

**Status:** Done

## Goal

Heat, tikka (artificial insemination), pregnancy checks and calvings are stored as records, not just dates on the cow.

## Already in place (from Phase 0)

- Optional sire and ear-tag fields on cows, and a unique ear tag per farm (source-level index).
- A breeding service that works out due dates from the dates on the cow (`services/breeding.js`).

## Scope

- A farm-scoped `BreedingEvent` collection: type (heat, service, pregnancy check, calving), date, cow, bull or outside straw (name and semen code), technician, result, notes.
- API: list (paged, per cow and per farm), create, edit, delete, with the same roles as other Dairy data.
- The existing date fields on the cow keep working; new events keep them in step (additive, no forced migration).
- Included in backup and restore, demo data and farm deletion (move/delete).

## Out of scope

- No screens (Phase 3).
- No automatic calf creation (Phase 4).

## Schema design (agreed before implementation)

`BreedingEvent` is a separate, timestamped, farm-scoped collection. It does not replace or rename the existing Cow fields.

- `_id`: string identifier, generated by the server.
- `farmId`: server-stamped by the existing MUF farm-scope model wrapper; never accepted from client input.
- `cowId`: required string ID of a female cow in the selected farm.
- `type`: `heat`, `service`, `pregnancy_check`, or `calving`.
- `date`: required valid `YYYY-MM-DD` date.
- `sireSource`: `farm_bull`, `outside_bull`, or `outside_straw` (optional except when a sire is supplied).
- `bullId`: optional ID of an in-farm male animal; only valid for `farm_bull`.
- `bullName`: optional external bull name; required for `outside_bull` and `outside_straw`.
- `semenCode`: optional semen identifier; required for `outside_straw`.
- `technician`, `result`, `notes`: optional trimmed text with server-side length limits.
- `createdAt`, `updatedAt`: managed timestamps.

API contract: preserve the existing `GET /api/breeding` calendar response. Add `GET /api/breeding/events` with optional `page` (1-based), `limit` (default 50, maximum 200), `cowId`, `type`, `from`, and `to` filters; paged responses return `{ events, total, page, limit, pages }`. Add `POST /api/breeding/events`, `PUT /api/breeding/events/:id`, and `DELETE /api/breeding/events/:id`. All event reads/writes are scoped to the selected farm. All three roles can create/edit records; only owner/manager can delete records.

Date synchronization: latest heat event updates `Cow.heatDate`; latest service event updates `Cow.pregnancyDate` (the legacy breeding-date field used by the current calculator); latest calving event updates `Cow.calvingDate`. Deleting or editing an event recomputes these fields from remaining events rather than blindly clearing them. A calving event does not create a calf; that remains Phase 4.

## Steps

1. Schema and API contract documented above before implementation.
2. Add the model, scope it with the farm layer, and add validated routes while preserving the existing calendar endpoint.
3. Wire the collection into manual and monthly backup/restore and farm deletion.
4. Add realistic memory-mode demo events and regression tests.

## New command-line check

`tests/dairy-breeding-events.test.ts` plus `npm run check-breeding-events` (also invoked by `npm run check-farms`): real-HTTP memory-mode checks cover create/edit, pagination, farm isolation, date validation, worker create/delete permissions, legacy date synchronization, and backup/restore retention. The checker never connects to MongoDB.
